# FolioWeave 平台化复审 · 2026-10-08

> 后续实施状态：本文保留改造前的评审快照。路由/插槽加载隔离、共享文章语义、目标项目构建上下文、模板切换、配置与发布写入一致性、扩展依赖约束及相关回归检查已落实到代码。当前接入方式以 `TEMPLATES.md`、`PLUGINS.md` 和 `src/core/contracts.ts` 为准；下文中的“尚未实施”描述仅对应评审时点。

评审对象：`codex/templates-plugins` 工作区中尚未提交的多模板与插件改造。本文记录该时点的事实、推断和建议，不代表这些后续优化已经实施。第二个真实模板尚未接入。

结论：已有可运行的多模板与共享 UI 插件基础，但还需要收敛加载边界、内容契约、构建上下文和验证体系，才能长期承接多个设计。当前不需要推倒重写，也不需要引入大型插件框架。下一轮工作的收益应体现为更少的隐式依赖、更少的重复流程和更可靠的接入验证。

**范围与证据**

- 阅读核心契约、模板与插件注册/生成、Classic 实现、CLI/向导、内容发布、路由、Markdown、样式、浏览器测试和 CI。
- 按 AGENTS.md 阅读安装版本 Next.js 的本地懒加载指南，并参考 React 性能技能检查模块依赖与客户端边界。
- 针对现有生产构建启动独立本地服务，用 Chromium 的独立浏览器上下文访问 `/`、`/blogs`、`/brink/privacy`，同时检查真实资源响应和页面 script/stylesheet 标签。
- 在项目内临时目录创建 `audit-probe` 模板，只调用读取和准备接口，复现目标项目目录与扩展目录不一致的问题。未改写实际 `portfolio.json`。
- 复核上一轮保留的运行性能失败与对照报告。本轮没有重新运行全部功能、视觉和性能套件；此前通过的套件不能替代新发现问题的验证。
- 本轮仅新增评审文档；临时脚本、结果和沙箱在检查后清理，独立测试服务关闭。未提交或推送。

**总体判断**

| 维度 | 当前基础 | 尚需补足 |
| --- | --- | --- |
| 通用性 | 同技术栈模板有统一入口，选择与作者内容分开 | 内容模型仍带有 Classic 的必填字段和数据访问习惯 |
| 可扩展性 | manifest、API 版本、选项校验、插槽和脚手架可用 | 路由入口、内容语义、测试还没有完全成为独立契约 |
| 性能 | 默认插件关闭，音乐不预加载，评论由读者主动加载 | 活跃模板的首页代码进入其他路由；移动交互预算仍有失败 |
| 可维护性 | 作者源、生成产物、模板、插件已有目录边界 | 多条配置写入路径、隐式项目根、重复校验和缺少依赖约束 |
| 一致性 | 核心路由与 metadata 集中，插件使用公共 tokens | Markdown/结构化数据、语言、主题作用域和失败状态不完全一致 |
| 可靠性 | 写入前验证、生成输出锁和回滚、分支保护已有实现 | 配置源到发布快照的跨进程一致性尚未闭环 |
| 测试 | Classic 功能、视觉、生命周期与跨浏览器覆盖较多 | 实际多模板矩阵、内容契约、模块归属和并发发布覆盖不足 |
| 产品化 | 克隆项目后能通过本地 CLI 选模板、配插件 | 尚不是发布到 npm 的独立项目创建器；高级配置仍要求 JSON |

**值得保留的设计**

1. 每次构建选择一个模板。无需为了“通用”在浏览器加载所有模板或增加运行时模板路由器。
2. 扩展来自受信任的本地代码目录，manifest 只描述受约束的入口、选项与能力。普通作者配置不能指定任意可执行模块路径。
3. 生成代码只导入选中的模板、启用的插件，并生成对应网络来源声明。关闭插件后的配置与加载面得到控制。
4. 作者源和发布产物分开；媒体使用验证后的字节快照，生成输出提交有目标白名单、锁、日志和失败回滚。
5. 插件采用 CSS Modules、明确插槽和局部错误边界。音乐持久挂载，评论使用稳定文章标识，并处理超时、重试和卸载。
6. Classic 的视觉兼容性继续由原有基线约束。其他模板应建立自己的基线，不能修改 Classic 基线来掩盖接入差异。

**1. 接入前：把模板入口拆到路由边界，解决已确认的额外加载**

证据位置：`src/core/extensions.mjs` 的 `extensionOutputs`、`src/app/layout.tsx`、`src/templates/classic/index.tsx`、`src/core/template-context.ts`。

生成模块通过 `import * as implementation` 汇总整个模板，根布局读取这个对象中的 Layout。Classic 总入口同时导出 Home、导入样式，并提供博客视图。`templateContext` 又从同一个生成入口读取 options。目录分开之后，根布局的模块图仍能触达各页面实现。

本轮浏览器结果如下。gzip 大小由实际响应正文通过 Node `gzipSync` 计算，便于对比，不等同于线上 CDN 的最终压缩传输大小。

| 路由 | 含首页交互代码的 JS | 首页/Classic CSS | 博客 CSS |
| --- | --- | --- | --- |
| `/` | 30,971 B，script 标签实际加载 | 19,244 B，实际加载 | 2,840 B，实际加载，但无博客主体 |
| `/blogs` | 30,971 B，script 标签实际加载，无首页主体 | 19,244 B，实际加载 | 2,840 B，实际加载 |
| `/brink/privacy` | 30,971 B，script 标签实际加载，无首页主体 | 19,244 B，实际加载 | 2,840 B，实际加载，但无博客主体 |

该构建中的 JS 为 `05rx20vdpp3lb.js`，包含 `mobile-menu-toggle`、`card-polaroid` 等首页交互内容；对应 CSS 为 `1g5u9qnrco5oq.css` 和 `2v1qpc4q_2-ld.css`。哈希文件名只适用于本次构建。

这是已发生的模块加载耦合。不能据此承诺拆分后一定精确节省 30,971 B，因为该 chunk 可能混有公共代码，构建器也会重新分组。现有 260 KiB JS / 30 KiB CSS 总量预算允许这些路由通过，没有验证“某路由不应依赖某功能”。

建议：manifest/生成器提供明确的 layout、home、blogIndex、blogPost、blogTag 入口；根布局只引用常驻壳层和常驻插件。模板 id/options 的生成模块不引用视图。页面样式在对应页面入口导入，公共样式只保留确实公共的部分。插件生成入口也按插槽拆分，避免文章专属插件经根布局的统一 PluginSlot 进入全站依赖图；这一插件影响目前属于静态结构判断，尚未测量启用插件后的各路由字节数。

单纯添加更多 `await import()` 不足以证明隔离成立。已安装 Next.js 文档明确提醒，Server Component 动态导入 Client Component 存在自动代码拆分限制，必须检查最终生产产物与浏览器请求。

验收：独立访问博客/隐私页不请求首页专属模块；首页不请求文章专属样式；文章插件未启用或不在适用路由时不加载其专属客户端代码；音乐跨客户端导航继续播放；总量预算和模块归属检查同时通过。

**2. 接入前开始、第二模板接入时验证：建立真正独立的内容契约**

证据位置：`src/core/contracts.ts`、`src/core/template-context.ts`、`portfolio.schema.json`、`src/portfolio/index.ts`、`src/templates/classic/home-page.tsx`。

`TemplateContext.introduction` 只是 `PortfolioConfig["hero"]` 的别名，biography 同样沿用 about。作者 schema 仍要求 hero、about、photography、footerBook、interlude 等结构。模板可以不显示这些内容，但作者仍须满足旧模型的必填要求。

同时存在两条数据通路：新模板使用 context；Classic 的 Home 不接收 context，许多组件直接读取 `@/config/site` 或 `@/portfolio`。共享的 resume-printer、instax-camera 也读取全局配置。这使 Classic 尚不能作为“仅依赖统一接口”的参考实现，并让组件难以在独立 fixture 中复用。

建议先保留现有作者 schema，增加显式适配层，把中立的身份、简介、项目、文章、媒体、导航能力整理成发布模型；Classic 特有的书本、段落动效和布局参数留在 Classic 适配器。Classic 和新模板都通过相同契约读取公共内容。共享交互组件接收所需的少量 props，避免把整份站点对象送进客户端组件。

不应根据尚未完成的第二模板，立刻创造一个覆盖所有网站类型的大 schema。等真实差异明确后，再设计带版本和迁移的作者配置升级；旧 profile 应能通过适配继续工作，迁移必须可预览并保留原始源文件。

验收：使用两个不同 fixture 能独立渲染同一共享组件；新模板不直接导入 Classic 或整份全局 profile；仅博客/无摄影等最小内容集有明确支持方式；切换模板不删除作者未展示的内容和模板设置。

**3. 接入前：统一文章语义与 SEO 责任**

证据位置：`scripts/template-scaffold.mjs`、`src/components/blog/markdown-blog-post.tsx`、`src/app/blogs/[slug]/page.tsx`。

脚手架目前用裸 ReactMarkdown；Classic 使用 remark-gfm、预计算标题 id、图片尺寸和加载策略等处理。`BlogPostingJsonLd` 也放在 Classic 使用的文章视图里，核心文章路由没有输出它。因此直接采用脚手架的新模板会出现表格/标题锚点语义和文章结构化数据差异，尽管 route metadata 仍集中生成。

建议把 Markdown 语义、标题 id、媒体信息和链接策略提取成无 Classic 布局样式的公共文章渲染能力；文章结构化数据由核心路由输出一次。模板决定排版、导航、目录是否可见和代码块外观。裸 ReactMarkdown 本身并不意味着安全漏洞，问题是相同内容缺少一致的产品契约。

脚手架还应按发布能力处理 Writing 链接和 Work 区块，避免空文章站点链接到不可用列表。脚手架应是最小但完整的契约示例，不能让每个模板作者重新发现这些要求。

验收：同一篇包含 GFM 表格、重复标题、图片和外链的 fixture，在两个模板中保留相同标题锚点、链接目标、媒体语义和恰好一份文章 JSON-LD；布局允许不同。

**4. 接入前：让项目目录成为显式构建上下文**

证据位置：`scripts/content-build.mjs`、`scripts/generate-portfolio-contract.mjs`、`scripts/extension-wizard.mjs`、`src/portfolio/publication-policy.mjs`。

`prepareContent(root, candidate)` 从 root 读取 schema，却调用未传 catalog 的 `resolveExtensions(config)`；后者默认读取实现模块所在项目。`prepareContract` 与扩展向导也存在默认目录依赖。路由策略在模块顶层导入本项目的 routes.json。

本轮创建了只有 `audit-probe` 模板的临时项目：`loadCatalog(sandbox)` 返回该模板，`prepareContent(sandbox, candidate)` 却返回 `Unknown template: audit-probe`。这证明现有 root 参数不能保证整条准备链使用同一项目。普通仓库内 CLI 目前使用固定本项目路径，不代表日常命令普遍失败；问题会影响隔离测试、未来独立 CLI 和多项目调用。

建议构造一个只属于本次准备任务的 ProjectContext，显式持有 root、catalog、route definitions、schema 和编译好的 validators。准备、合同生成、校验和向导共享该上下文。不要创建进程级永不失效的可变全局缓存，否则开发模式下 manifest/schema 更新会变成另一种隐患。

`assertProjectPublicationAllowed` 当前对非实现根目录且未给 targetBranch 的调用跳过保护。重构时应区分明确声明的隔离测试环境与普通目标仓库，普通路径参数不应隐含“允许跳过边界”。不得移除现有个人分支保护。

验收：两个项目使用同名但不同定义的模板和路由时互不串读；sandbox 单测无需复制一整套执行脚本才能正确定位目录；实际仓库发布始终执行自身分支/profile 边界检查。

**5. 接入前：收敛配置写入与发布事务**

证据位置：`scripts/profile-edit.mjs`、`scripts/personalize.mjs`、`scripts/content-build.mjs`、`scripts/atomic-output.mjs`。

已有的生成输出锁与回滚应保留。但 updateProfile 的顺序是读取配置、准备、检查源未变化、写入 profile，再进入生成输出锁。向导另有自己的写配置、启动构建、失败恢复流程。发布接口接收 prepared 快照时没有复核源版本。

由代码可推导的风险是：进程 A 准备旧内容，B 准备并发布新内容，A 随后取得输出锁仍可能发布旧快照。两个写配置调用也可能在“读取检查”和“实际写入”之间交错。本轮未实施并发故障注入，没有观察到实际作者数据损坏，不把这种风险描述成已发生事故。

建议所有配置命令和向导共用一次更新流程：项目级写入协调、源版本/指纹复核、基于同一候选内容准备、提交和失败恢复。耗时准备若放在锁外，提交前必须检查 revision；若先锁后准备，需要合理反馈锁持有者与状态。watcher 应识别一次完整发布，避免把逐文件替换当作多个独立版本。

不要直接把作者配置加入当前 `commitGeneratedOutputs` 白名单；该 API 明确只管理可再生文件。作者文件需要单独且有并发保护的更新协议，失败恢复也不能覆盖后来的手工编辑。

验收：并发命令、命令与 watcher、准备期间作者手改、输出写入失败都有可重复测试；过期快照拒绝提交或重新准备；任一失败后源与发布状态可解释，且作者后续编辑不被回滚覆盖。

**6. 接入前：从 Classic 测试扩展为平台契约加模板测试**

证据位置：`qa/visual-contract.mjs`、`qa/functionality.mjs`、`qa/cross-browser.mjs`、`qa/runtime-budget.mjs`、`qa/extension-browser.mjs`、`.github/workflows/ci.yml`。

现有视觉区域固定为 hero/about/work/photography/contact/lightbox，基线只分 demo/personal；功能和性能脚本使用 Classic 的菜单、拍立得、图库选择器。extension-browser 已证明一个沙箱模板能接入、插件能工作，并不等于尚未接入的第二个真实模板得到验证。

建议分成公共内容/路由/SEO/插件生命周期契约，以及各模板自己的视觉、交互、性能场景。基线身份包含 template、profile、平台和 viewport。让正式模板列表驱动构建与基础验证，而不只构建默认 Classic。插件覆盖核心单插件、代表性组合和不兼容失败，不必穷举 2 的 N 次方组合。

目前 qa:all 将 runtime 放在串行链开头，失败会阻止同链后续功能检查及同 job 的扩展验证。可拆成独立 CI 工作或收集各阶段状态后汇总失败，让性能问题与功能问题同时可见；性能失败仍应阻止通过，不能改成忽略。

验收：破坏第二模板文章标题或插件插槽会使其专属检查失败；更改 Classic 不会要求重拍其他设计基线；运行性能失败时仍能拿到独立功能检查结果；未经评审不自动刷新基线。

**7. 发布质量：运行性能仍有待解决的门槛**

前一轮 `qa/runtime-budget-report.json` 中 constrained、390px、reduced motion 的三个交互工作量 P95 样本为 119.5 / 160.5 / 110.5 ms，汇总中位数 119.5 ms，高于 100 ms 门槛。全部运行性能检查不能标为通过。

原首页代码在相同当前依赖、构建器和测试条件下的三个对照值为 147.6 / 213.5 / 149.8 ms，也超标。因此不能认定这次模板拆分造成该失败，也不能把有限、受宿主负载影响的对照包装成已证明的性能提升。完整事件时延、真实用户 INP 和这里的 interactionWorkP95 不是同一指标。

事件记录中多个高耗时 click 指向摄影卡片，已有样本的处理耗时约 101–149.5 ms；另有部分事件缺少目标。这只能帮助选择 trace 场景，不能直接锁定某个 React 函数为根因。

下一步先定位图库打开/关闭及菜单操作的主线程 trace，区分事件处理、React 提交、布局和绘制，再处理触发路径。路由加载隔离也应独立测量，不假定减少下载一定解决交互耗时。继续尊重 reduced motion，保持焦点恢复、滚动锁和图片预热行为，使用相同条件验证变化。

**8. 后续：用更少的来源维护类型与规则**

插槽集合在 extensions.mjs、contracts.ts 和 portfolio.schema.json 中分别声明。插件 options 的 JSON Schema 与手写 TS 类型也可能漂移。模板 API 有版本号，但作者配置升级尚没有相应的版本迁移协议。

建议沿用现有 JSON Schema/Ajv 与类型生成能力，定义一个权威插槽/manifest 描述并生成或校验其他表示。每次 ProjectContext 构造复用编译好的 validators，不要 resolve 一次就再编译一次。未来真正出现 API 破坏性变更时，提供可预览迁移；目前不必开发复杂版本范围解析器。

eslint 当前主要是 Next/TS 规则，尚未强制模板、插件间依赖方向。边界测试搜索 `@/demo/` 字面量也不能覆盖所有相对导入写法。补充能解析路径的依赖约束，禁止插件导入模板、模板导入其他模板、普通组件直接读取作者文件；生成组合入口是明确例外。原生 img 的全局规则例外应缩到有意保留原生行为的范围，不强制替换已验证的 DOM。

验收：新增一个插槽或插件 option 时无需手工同步多个不相关文件；非法别名和相对导入都能被检查发现；生成类型过期会使检查失败。

**9. 后续：统一插件使用体验，保留简单的扩展边界**

当前三个插槽足以承接音乐与评论。它们提供的是受信任 UI 扩展，不是任意服务端路由、数据库迁移或不可信远程代码的沙箱。此范围适合当前产品，不必为了将来可能出现的插件市场增加运行时安装、微前端、依赖注入容器或事件总线。

需要继续明确的实际接口：

- 布局如何放置持久 footer/floating 插槽。现在根布局把它们附在 children 后，模板不能直接把 footer 插槽放进自身 footer 内。可传入明确的 slot 节点，保持实例与生命周期稳定。
- 字体、表面、文字、强调色、焦点、层级等语义 tokens 的作用域。Classic 首页的动态主题位于 HomeExperience 子树，根布局插件不自然继承其动态前景色。主题跟随应有明确产品约定，不要求所有模板拥有同一种夜间滚动效果。
- locale 需要落实到标签和错误文案。评论的 lang 默认仍是 en，未使用传入的 context.locale；播放器和错误边界也有英文固定文案。可先提供小型内置文案字典与作者覆盖，不急于引入完整国际化框架。
- 错误边界只处理其适用的渲染错误；当前失败状态没有重试/reset。插件仍需自行处理异步错误与资源清理。可补统一的可恢复失败表现和开发诊断，不能宣称错误边界隔离所有第三方故障。

验收：插件在两个真实布局里有合理对比度、焦点状态、窄屏位置和语言；评论加载失败不阻断正文；客户端换页不重复创建常驻音乐实例；不支持的插槽在写配置前报错。

**10. 后续：减少构建重复工作与维护成本**

prepareContent 编译主 schema、解析扩展、逐一读取并测量所有引用媒体，再调用 prepareContract 重新生成类型、validator 并解析扩展。prebuild 的检查又准备当前 profile 和 demo。生成文件即使内容相同也会进入替换流程，发布目录会重新暂存。

这些选择对目前规模可以工作，还不足以据此宣称构建很慢。但照片、文章、音乐增长后，重复读取和 Buffer 快照会放大耗时与内存；目前只有部分图片尺寸预算，没有同等明确的音频大小/总量策略。

建议先记录各阶段时间、读取字节和峰值内存，再实施有边界的优化：按 schema/manifest 内容复用合同和校验器；只写内容变化的文本产物；媒体元数据缓存以内容一致性为前提；使用有上限的 I/O 并发。仍应验证未发布的作者源是否有效，不能简单跳过草稿校验来换取速度，也不能用可能在校验后变化的文件路径替代已验证字节快照。

CLI 的选项解析、向导、诊断应共享同一应用层。对具体命令不适用的 flags 应明确报错。当前配置方式适合开发者；面向非开发用户时，可以基于 optionsSchema 为常用字段提供逐项提示，JSON 文件保留为高级入口。独立 `create-folioweave` 发布包属于后续分发工作；现有 private 项目和 npm scripts 尚不提供这个产品形态。

**建议的实施顺序与停止条件**

| 阶段 | 改造内容 | 完成依据 |
| --- | --- | --- |
| A：第二模板接入前 | 分离路由/插槽生成入口；统一 ProjectContext；公共文章语义与 JSON-LD；统一写配置与发布协议 | 已复现的额外加载与 root 串读消失；并发发布和内容语义测试通过 |
| B：用第二模板检验抽象 | 中立发布模型加 Classic 适配；修正共享组件 props；真实模板测试矩阵；插槽布局与主题/语言契约 | 两个真实设计共用内容和插件，分别通过自身视觉、交互与公共契约 |
| C：基于测量优化维护成本 | 交互 trace 修复；去重复生成与媒体读取；单一规则来源；CLI 体验 | 原性能门槛通过，有同条件前后数据；无行为/视觉回归，日常新增模板所需修改点减少 |

性能失败应在宣称发布质量达标前解决；把 trace 工作放在测量阶段不等于降低或延后发布门槛。第二模板到达时可以在独立目录开始适配；先稳定入口、内容语义和测试契约，减少它接入后再次搬迁的成本。

目标依赖方向可以保持简单：作者源经统一构建上下文成为发布模型；核心路由负责内容与元信息；路由级模板视图决定呈现；插件仅依赖公共 SDK、传入数据和语义 tokens；生成组合模块负责连接选中实现。扩展只需新增自身目录和接入声明，通常不应修改核心业务判断。

最终判断是否“更通用、更易维护”的依据是：第二模板不需要复制内容逻辑，新增插件不需要改 Classic，新增路由不携带首页专属资源，作者改一次配置只有一条发布路径，失败能被对应测试准确捕获。满足这些条件之后，再扩展目录和能力才有明确收益。
